# AUDIT-2026-08-20.md — API contract audit, scoped to the observatory-pipeline integration

Conducted 2026-08-20 by six independent reviewers, each reading the actual PHP/CodeIgniter4
source of one subsystem (`frames`, `sources`/`source_observations`, `anomalies`,
`tasks`/`task_items`, `source_charts`, and the shared `SkyMath`/`settings`/auth layer) against
what `observatory-pipeline` — this API's one real client — actually sends and reads, per that
repo's own `CLAUDE.md` and this repo's `docs/API.md`/`CLAUDE.md`. This is **not** a general
code-quality review: findings are scoped to correctness of the pipeline↔API contract, not PHP
style. Every finding below was verified by reading the actual implementation (file:line quoted),
not inferred from documentation alone; several suspected risks were checked and explicitly
cleared rather than assumed.

**Totals:** 2 critical, 1 high, 4 medium, 7 low findings, plus a substantial list of
specifically-verified-correct mechanisms (including the single highest-risk item this audit was
commissioned to check — see "Verified correct" below).

Severity guide (same bar as the companion pipeline-side audit,
`observatory-pipeline/docs/AUDIT-2026-08-18.md`):
- **Critical** — a mechanism that can silently drop/duplicate/corrupt data for a whole class of
  requests, with no distinguishing log line.
- **High** — systematic distortion or loss, but narrower in scope than Critical.
- **Medium** — real, but triggered by a specific, less common condition.
- **Low** — worth knowing/fixing, but not currently causing systematic data loss.

## Critical findings

### ✅ DONE — C1. `POST /frames/{id}/anomalies` deletes-then-inserts with no transaction — a failed insert permanently and silently zeroes a frame's anomalies

**Fixed (2026-09-22):** `saveAnomalies()` runs the delete and the insert inside one manual
transaction (`transBegin`/`transCommit`, with `transRollback` in a `catch (\Throwable)`), so an
insert failure — including the `DatabaseException` that `DBDebug = true` throws, which the old
`=== false` check never saw — rolls the delete back and answers `500` (retryable by the pipeline)
with the frame's previous anomalies intact. Manual rather than `transStart`/`transComplete` so the
thrown exception is caught here and turned into the status code the client's retry policy keys on.
The empty-list short circuit moved inside the transaction: it is the same replace, just with
nothing to insert. Regression tests: a batch carrying an FK-violating `source_id` leaves the two
earlier anomalies in place; an empty batch still clears them.

**Location:** `app/Controllers/Api/V1/FramesController.php:564` (delete) through `:660-664`
(insert), in `saveAnomalies()`.

No `$db->transStart()`/`transComplete()` wraps the delete-existing/insert-new pair — each is its
own auto-committed statement. This repo already has the correct fix pattern, just not applied
here: `saveSources()`'s own reconciliation delete+insert block (lines 463-484) explicitly wraps
itself in a transaction; `saveAnomalies()` was never given the same treatment.

**Scenario:** `insertBatch()` fails after the delete has already committed — a stale/deleted
`source_id` violating the FK, a dropped connection, a lock-wait timeout, or the process
crashing/OOMing mid-request. With `DBDebug = true` (`app/Config/Database.php:36`) and no open
transaction, a real DB error here doesn't even return `false` — `BaseConnection::query()` throws
an uncaught `DatabaseException`, bypassing the `=== false` check entirely.

**Consequence:** the frame's `anomalies` rows are gone, permanently, indistinguishable from
"this frame genuinely has none." The pipeline compounds this: `api_client/anomalies.py` retries a
5xx 3 times then swallows the exception and returns `None` — `worker.py` marks the
`DETECT_ANOMALIES` task `COMPLETED` regardless. If the failure is deterministic (a persistently
stale `source_id`), all 3 retries fail identically and nothing anywhere records that this was
"delete succeeded, insert failed" rather than "zero anomalies found." This directly compounds the
companion pipeline audit's own C8 finding (a crashed classify run can post an empty anomaly list)
— the API side currently has no safety net against it.

**Fix direction:** wrap the delete/insert pair in `$db->transStart()`/`transComplete()`, mirroring
`saveSources()`'s existing pattern, and check `transStatus()` before returning success.

### C2. No atomic task claiming — two concurrent workers can both process the same task

**Location:** `app/Controllers/Api/V1/TasksController.php:225-263` (`update()`), no locking
helper anywhere in `TaskModel`/`TaskItemModel`; `worker.py:452-462` on the pipeline side.

`GET /tasks?status=PENDING&limit=1&order=asc` is a plain, unlocked `SELECT`. The worker's claim,
`PATCH /tasks/{id} {"status":"RUNNING"}`, is implemented as an unconditional `update($id, $data)`
with **no `WHERE status = 'PENDING'` guard and no affected-rows check**. Two worker processes
polling concurrently — a deploy overlap, or an accidentally-scaled `worker` service — will both
see the same PENDING task, both successfully PATCH it to RUNNING, and both dispatch the exact same
full item list, since both read `items` before either has written anything back.

**Consequence:** duplicate astrometry/catalog-query/photometry/anomaly-detection/chart-rendering
work for every item in the task, and duplicate load on Gaia/Simbad/2MASS/Pan-STARRS/MPC. Durable
state usually still converges correctly (`frames.filename` is UNIQUE and upserted; sources
reconcile by `frame_id`; anomalies fully replace; charts upsert by `(source_id, style)`) — so this
is "wasted compute + doubled external traffic + last-writer-wins on freshly recomputed values"
rather than permanent duplicate rows — but the waste and the silent overwrite of one worker's
result by the other's are both real and currently unmitigated.

**Fix direction:** claim atomically — `UPDATE tasks SET status='RUNNING' WHERE id=? AND
status='PENDING'`, check affected-rows before proceeding (or use `SELECT ... FOR UPDATE` inside a
transaction).

## High-priority findings

### H1. `POST /tasks/{id}/items/progress`'s per-item "already resolved" guard is check-then-act, not atomic

**Location:** `app/Controllers/Api/V1/TasksController.php:302-325`.

The guard that's supposed to make duplicate progress delivery safe (`if ($item['status'] !==
'PENDING') { ...note: 'Already resolved'...; continue; }`) is a read-then-write with no row lock —
exactly the shape Finding C2 makes exploitable. Two concurrent progress reports for the same item
can both read `PENDING` before either writes, and both fall through to `update()` and increment
`TaskModel::bumpProgress()`'s counters.

**Consequence:** `completed_items + failed_items` can durably exceed `total_items` (e.g. `2/1` on
a single-item task), a wrong aggregate visible via `GET /tasks/{id}` and the operator UI. For
`DELETE_FRAME` specifically, this also double-invokes `FrameModel::deleteWithDependents()` for the
same `frame_id` — verified idempotent in practice today (FK cascades make the second call a
no-op), so no crash, but incidental rather than designed-for.

**Fix direction:** same pattern as C2 — `UPDATE task_items SET status=? WHERE id=? AND task_id=?
AND status='PENDING'`, and only count/cascade when exactly one row was affected.

## Medium-priority findings

### M1. Two distinct uncatalogued sources within the 2″ coordinate-fallback radius, in the *same* `POST /frames/{id}/sources` batch, silently collapse into one row

**Location:** `app/Controllers/Api/V1/FramesController.php:354-445` (`saveSources()`).

The per-source loop has no transaction boundary and runs synchronously, so an INSERT from
iteration *N* is already visible to iteration *N+1*'s `findByCoordinates()` lookup within the
same request. Two uncatalogued sources A (earlier in the array) and B (later, within 2″ of A)
both resolve to the same `sources.id`; B's data then goes through the `update()` branch and
**overwrites** A's `mag`/`flux`/`fwhm`/`snr`/`elongation`/`ra`/`dec`. No unique-key violation is
ever raised (the code always SELECTs first), so nothing is logged.

**Scenario:** two ordinary uncatalogued, non-subtraction detections close together in a crowded
field or near a galaxy — e.g. a genuine `SUPERNOVA_CANDIDATE` next to an unrelated faint star, or
a deblended pair. None of the pipeline's own three dedup passes
(`_dedupe_by_catalog_identity`, `_dedupe_unmatched_near_matched`,
`_dedupe_uncatalogued_subtraction_pair`) close this gap — all three deliberately leave two
ordinary uncatalogued, non-subtraction sources alone, since they might be two real distinct faint
objects.

**Consequence:** both original detections end up sharing one `source_id`, whose stored photometry
reflects only the *second* of the two — the first's measurement is lost with no trace, and any
two anomalies attached to these positions get aliased onto one object.

**Fix direction:** when `findByCoordinates()` resolves to a `sources.id` already confirmed
*earlier in this same batch*, treat that differently from an ordinary cross-frame re-match — at
minimum log a warning distinguishing the two cases; ideally keep both as distinct detections
rather than silently merging.

### M2. `POST /frames` never validates that `obs_time` is parseable

**Location:** `app/Controllers/Api/V1/FramesController.php:86` —
`'obs_time' => date('Y-m-d H:i:s', strtotime($body['obs_time']))`.

Every other date-parsing call site in this same controller (`covering()`, `coveringBatch()`,
`index()`'s `date_from`/`date_to`, `nearestBefore()`) explicitly guards against `strtotime()`
returning `false`. `create()` is the one exception, despite `obs_time` being required.

**Scenario:** `obs_time` comes straight from the pipeline's `fits_header.py`, which passes a raw
FITS `DATE-OBS`/`TIME-OBS` header string through with no format validation (see the companion
pipeline audit's C10 for the corresponding pipeline-side gap). A non-ISO8601 or corrupted header
value isn't caught by the required-field presence check, which only checks for missing/empty/null.

**Consequence:** `strtotime()` returns `false`; `date('Y-m-d H:i:s', false)` silently coerces to
`"1970-01-01 00:00:00"`. The frame registers successfully (`201`), no error, no log line. This
corrupts `GET /frames`'s ordering, `GET /frames/covering`'s `before_time` filtering, and
`object_stats.first_obs_time`/`last_obs_time` for that object — with the pipeline having no way
to detect it happened from the response it gets back.

**Fix direction:** validate `strtotime($body['obs_time']) !== false` before building `$data`;
return `400`/`422` consistent with every other date-validation site in this file.

### M3. `source_charts` upsert-by-`(source_id, style)` is check-then-act, not atomic — real race, but currently self-healing

**Location:** `app/Models/SourceChartModel.php:98-121` (`upsertForSource()`) and `:161-184`
(`upsertForTaskItem()`).

Both do a `SELECT` then branch to `update()`/`insert()` with no transaction or locking `SELECT`,
despite a real unique key backing each. Two concurrent uploads for the same `(source_id, style)`
(a client-side retry racing the original request, or two workers) can both pass the
"doesn't exist yet" check and both attempt `insert()`; the loser's INSERT hits the unique-key
violation, which — under this repo's `DBDebug = true` — surfaces as an uncaught `DatabaseException`
→ HTTP 500, correctly retryable per the pipeline's 5xx-only retry policy. The retry then succeeds
via the UPDATE branch.

**Consequence:** no duplicate rows, no silent data loss today — just an extra retry and log noise.
Flagged as Medium (not Low) because it depends on the current `DBDebug`/exception-handling
configuration to self-heal; a future change to error handling (e.g. `DBDebug = false` in some
deployment, or a caught-and-swallowed exception) would turn this into a silent lost-update instead.

**Fix direction:** use a real atomic upsert (`INSERT ... ON DUPLICATE KEY UPDATE`) or wrap the
check+write in a transaction with a locking `SELECT`.

### M4. `observatory-api`'s own `CLAUDE.md` misdescribes `RESTART`'s actual creation behavior

**Location:** `CLAUDE.md:69-70` vs. `app/Controllers/Api/V1/TasksController.php:41-137`
(`create()`).

The doc claims a `RESTART` task is auto-marked `COMPLETED` upon creation since it has no items.
The actual code inserts every task type — `RESTART` included — with `'status' => 'PENDING'`
unconditionally; there is no branch anywhere in `create()` that completes it early. What actually
happens (and what the *pipeline's* own `CLAUDE.md`/`worker.py` correctly describe): `RESTART` sits
`PENDING` in the FIFO queue like any other task, and only reaches `COMPLETED` once the worker picks
it up (correctly, via its own zero-items special case), raises `RestartRequested`, and PATCHes it
complete before exiting.

**Consequence:** not a functional bug — `worker.py` already handles a queued, non-pre-completed
`RESTART` correctly — but a maintainer relying on this repo's own documentation (e.g. to build a
dashboard assuming `RESTART` never appears `PENDING`, or to simplify `create()` believing
completion logic lives elsewhere) will be misled. An operator creating `RESTART` expecting instant
effect will instead see it queued behind whatever else is pending.

**Fix direction:** either make `create()` actually complete `RESTART` at insert time (matching the
doc), or correct the doc to describe the real PENDING→picked-up→COMPLETED flow.

## Verified correct (checked because they looked like plausible risk areas)

- **Positional alignment of `source_ids` in `POST /frames/{id}/sources`** — the single highest-risk
  item this audit targeted. Verified line-by-line: every exit path of the per-source loop
  (invalid input, insert failure, matched-existing, newly-created) appends exactly one entry to
  the response array before continuing, including both early-`continue` paths — no scenario shifts
  the array out of alignment with the input. Covered by an existing regression test,
  `testSourceIdsAlignPositionallyAndNullOutSkippedEntries`.
- **Catalog-identity-before-coordinate matching order** in `saveSources()` — verified as the only
  call site, no bypass anywhere; covered by a regression test reproducing the exact real incident
  (`2014 RY1` vs. a nearby Gaia star) this ordering exists to prevent.
- **Pointing-error "keep first value" semantics** — fully implemented via a real upsert-by-`filename`
  (unique constraint backed); `pointing_error_*` fields are only ever set on the
  newly-created-row branch, never touched on an update, including the "starts NULL, stays NULL"
  case. Covered by dedicated regression tests.
- **`POST /frames/covering/batch`** — `SkyMath`'s dec-scaled RA margin and RA=0/360 seam splitting
  are both correct (verified against worked examples and pole/seam-specific regression tests); the
  `(object)` cast defeating PHP's array re-canonicalization is present and correct on all three
  batch endpoints (`near/batch`, `covering/batch`, `tracks/batch`).
- **QC-failed (zero-source) frame handling** — no join anywhere in the codebase drops a zero-source
  frame from a listing/stats computation; `object_stats` counts it correctly regardless of
  `quality_flag`.
- **`anomaly_type` closed-set consistency** — the 10 values in `AnomalyModel::ALLOWED_TYPES`, the
  migration's `ENUM` constraint, and the pipeline's own `AnomalyType` enum were compared
  character-by-character; no mismatch.
- **Anomalies validation-before-delete ordering** — literally verified: every row's `anomaly_type`
  is validated, and the whole request rejected with `400` on any failure, entirely before the
  existing-rows `DELETE` runs. A malformed batch cannot reach the delete.
- **RESTART's worker-side handling** — despite the API-doc mismatch (M4), `worker.py` correctly
  treats a zero-item `RESTART` as dispatchable rather than hanging, and marks it `COMPLETED` after
  handling `RestartRequested`.
- **Bare filename resolution** — confirmed `Web\FramesController::createTask()` really does build
  task items from a bare `frames.filename` basename, matching the pipeline's
  `_resolve_bare_filename()` assumption exactly, including its already-mitigated
  zero/multiple-match edge cases.
- **`GENERATE_CHARTS` payload shape** — confirmed an item created with no `payload` key stores real
  SQL `NULL`, decoded to JSON `null`, read by the pipeline as `None` — identical to a genuinely
  missing key, no empty-string mismatch.
- **Chart magic-byte validation** — PNG/GIF signatures checked at the correct offsets/bytes; a
  mismatch is rejected with a genuine `400`, verified by passing regression tests.
- **Dual-key (`source_id`/`task_item_id`) exclusivity and the FK-less `task_item_id` design** — both
  are conventions rather than enforced constraints, exactly as documented, and currently
  unexploited: no code path ever deletes a `tasks`/`task_items` row (no route exists for it), and
  the one feature that touches `source_charts` beyond the two upload paths
  (`SourceModel::mergeSources()`) never reassigns `source_id` in place.
- **Retry-discipline / HTTP status code inventory** — swept every endpoint the pipeline actually
  calls; validation failures consistently return `400`/`404`/`422` (never retried, correctly), and
  only genuine DB/server failures return `500` (correctly retried) — no misclassification found in
  either direction, across all six audited areas.
- **`SkyMath` unit consistency, RA-seam handling, and dec-scaled RA margin** — every call site
  converts to the same units `SkyMath` expects; the seam-splitting and pole-clamping (`cos(dec)`
  division, not multiplication, with an explicit `abs(cos) < 0.0001` guard returning 180°) both
  match their own unit tests exactly.
- **Settings config/internal split and the pipeline heartbeat** — `GET /settings` genuinely excludes
  `type='internal'` rows; the heartbeat filter genuinely gates on the actual response status code
  being 2xx (not "no exception thrown"), and the API-key filter is applied to the entire `api/v1`
  route group with no gaps.

## Where to start

Five changes with the best effect-to-effort ratio:

1. **C2** — atomic task claim (`UPDATE tasks SET status='RUNNING' WHERE id=? AND status='PENDING'`,
   check affected rows). Closes the highest-blast-radius issue: duplicate processing of an entire
   task under any concurrent-worker scenario.
2. **C1** — wrap `saveAnomalies()`'s delete+insert in a transaction, mirroring `saveSources()`'s
   own existing pattern in the same codebase. Small, mechanical, closes a real silent-data-loss
   path that directly compounds a known pipeline-side risk.
3. **H1** — the same atomic-claim pattern as C2, applied to `postItemsProgress()`'s per-item guard.
   Fixes counter corruption and the incidental double `DELETE_FRAME` cascade.
4. **M1** — in `saveSources()`, treat a same-batch coordinate-match to a source confirmed earlier
   in that same batch as a distinct case from an ordinary cross-frame re-match, rather than
   silently overwriting the first detection's photometry.
5. **M2** — validate `obs_time` is parseable in `POST /frames`, matching every other date-handling
   call site already in the same file.
